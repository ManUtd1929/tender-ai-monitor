# Tender AI Monitor

## Цель проекта

Создать автоматизированную систему мониторинга тендеров и закупок, опубликованных на сайте:

https://gnumner.minfin.am/

В перспективе система должна уметь:

1. Отслеживать новые объявления о закупках.
2. Определять, какие тендеры были опубликованы недавно.
3. Фильтровать тендеры, связанные с:

   * логистикой;
   * грузоперевозками;
   * транспортными услугами;
   * доставкой;
   * международными перевозками;
   * таможенными услугами;
   * другими закупками, релевантными деятельности компании.
4. Скачивать прикрепленные к тендерам документы, например PDF и DOCX.
5. Извлекать текст из тендерной документации.
6. Анализировать релевантные тендеры с помощью LLM/ИИ.
7. Формировать структурированное краткое описание тендера.
8. Сохранять обработанные тендеры в базе данных.
9. Не допускать повторной обработки одного и того же тендера.
10. Отправлять релевантные тендеры в Telegram.

---

## Правила разработки

### 1. Не придумывать данные

Никогда не придумывать:

* названия тендеров;
* даты;
* CPV-коды;
* заказчиков;
* ссылки;
* содержимое документов;
* требования тендера;
* HTML-селекторы;
* API endpoints.

Если какая-либо информация неизвестна, сначала необходимо проверить реальный источник.

---

### 2. Не угадывать структуру сайта

Перед реализацией парсинга сайта необходимо:

* изучить реальный HTML;
* при необходимости изучить сетевые запросы сайта;
* определить, как работает пагинация;
* определить идентификаторы тендеров;
* определить ссылки на вложения;
* проверить, загружаются ли данные динамически.

Нельзя придумывать CSS-селекторы или структуру страниц без предварительной проверки.

---

### 3. Сохранять модульную архитектуру

Следующие части проекта должны быть разделены:

* сбор данных с сайта;
* обработка документов;
* фильтрация;
* AI-анализ;
* база данных;
* Telegram;
* конфигурация.

Нельзя смешивать всю бизнес-логику в одном файле.

---

### 4. Предпочитать простые решения

Предпочитать:

* понятный Python-код;
* небольшие функции;
* явную логику;
* читаемый код.

Избегать без необходимости:

* сложных абстракций;
* лишних классов;
* фреймворков;
* сложных архитектурных паттернов.

Использовать их только тогда, когда это действительно оправдано.

---

### 5. Никогда не хранить секреты в коде

Нельзя записывать непосредственно в Python-файлы:

* API-ключи;
* Telegram Bot Token;
* пароли;
* данные доступа к базе;
* другие секретные значения.

Использовать переменные окружения и файл `.env`.

---

### 6. Логирование

Важные этапы работы программы должны записываться в логи.

Например:

* запуск парсера;
* успешное получение страницы;
* обнаружение нового тендера;
* пропуск уже обработанного тендера;
* загрузка документа;
* ошибка обработки документа;
* результат классификации тендера;
* отправка сообщения в Telegram;
* ошибка API.

---

### 7. Защита от дубликатов

Один и тот же тендер не должен обрабатываться или отправляться в Telegram повторно.

Для определения уникальности тендера в дальнейшем следует использовать стабильные идентификаторы, например:

* ID тендера;
* URL тендера;
* ID объявления;
* ID документа.

Не следует определять уникальность только по названию тендера.

---

### 8. Результат работы ИИ

AI-анализ должен возвращать структурированные данные.

Предпочтительный формат:

* JSON;
* либо другой строго валидируемый структурированный формат.

Нельзя использовать неконтролируемый свободный текст для критически важных полей.

---

### 9. Сохранять связь с источником

Для важных извлечённых данных по возможности необходимо сохранять источник.

Например:

* страница тендера;
* прикрепленный документ;
* URL;
* имя файла.

Нельзя представлять предположение ИИ как факт, извлечённый из документа.

---

### 10. Не менять архитектуру проекта без объяснения

Перед существенным изменением архитектуры необходимо:

1. Объяснить предлагаемое изменение.
2. Объяснить, зачем оно необходимо.
3. Указать, какие файлы будут затронуты.

Не перестраивать проект автоматически без объяснения.

---

### 11. Разрабатывать проект поэтапно

Не реализовывать будущие этапы проекта без явного запроса.

Предварительная последовательность разработки:

1. Изучение сайта.
2. Создание сборщика тендеров.
3. Защита от дубликатов.
4. Добавление базы данных.
5. Фильтрация тендеров.
6. Скачивание вложений.
7. Обработка PDF/DOCX.
8. AI-анализ.
9. Интеграция Telegram.
10. Автоматический запуск по расписанию.
11. Размещение системы на сервере.

---

### 12. Тестирование

При реализации важной логики необходимо:

* создавать небольшие тесты там, где это оправдано;
* тестировать парсинг на реальных сохраненных примерах;
* проверять защиту от дубликатов;
* проверять формат структурированного AI-ответа.

Если код можно запустить и проверить, нельзя утверждать, что он работает, не выполнив тест.

---

### 13. Обработка ошибок

Программа не должна полностью прекращать работу из-за ошибки при обработке одного тендера или одного документа.

По возможности ошибки должны обрабатываться отдельно.

В логах необходимо сохранять достаточно информации, чтобы потом понять причину проблемы.

---

### 14. Изменение существующего кода

Перед изменением уже существующего кода необходимо:

* сначала изучить текущую реализацию;
* не переписывать работающий код без необходимости;
* вносить точечные изменения;
* объяснять важные изменения.

---
